# Maestro 開発計画

Maestro は、Claude Code、Codex、Antigravity CLI、OpenCode といったコーディングエージェントの CLI を、
1つの GUI（gpui）と TUI（ratatui）から統括するデスクトップアプリケーションです。

## 前提となる設計方針

- **コアとフロントエンドの疎結合**: 状態と処理はすべてデーモン（`maestro-daemon`）が持ちます。GUI と TUI は
  `maestro-client` を通して同じコマンドを送り、同じイベントを受け取るだけです。
- **操作する PC と作業サーバーの分離**: デーモンは作業サーバー上で動き、フロントエンドは
  `ssh host maestro-daemon --stdio` でつなぎます。認証は ssh に任せるので、Maestro 自体はポートを開けず、
  鍵も扱いません。
- **指揮官とワーカーの分離**: ユーザーと会話して計画を立てるのは指揮官エージェントだけです。実際の作業は、
  ワークフローの各ノードに割り当てたワーカーエージェントが行います。指揮官はファイルを編集しません。
- **ワークフローは DAG**: エージェント間の依存関係や階層は有向非巡回グラフで表し、GUI では ComfyUI 風の
  ノードエディタとして表示します。指揮官とユーザーは、同じ操作で同じグラフを編集します。
- **デザイン**: [uthree/design-language](https://github.com/uthree/design-language)（Atelier, Glass）に従います。
- **参考実装**: [uthree/auris-studio](https://github.com/uthree/auris-studio) の `auris-agent` に、4つの CLI
  それぞれのバックエンドと gpui-flow によるノードグラフ表示があります。

## ステップ

### 1. ワークスペースとコアの骨格

- 仮想ワークスペースを作り、`maestro-core`（ドメインモデル）、`maestro-protocol`（コマンドとイベント）、
  `maestro-daemon`（状態の持ち主）、`maestro-client`（接続）に分けます。
- 接続方法は、同一プロセス内、ローカルの子プロセス、SSH 先の3つです。

### 2. プロバイダ層と実行環境

状況: 実装済み。4つのアダプタすべてで、実機の CLI を使ってテキストのターンを確認しました（Claude Code は
クラウド環境、Codex / Antigravity CLI / OpenCode は macOS、2026-10-28）。権限要求は Claude Code で、
拒否までの流れを確認済みです。Codex はワークツリー内の読み取りを承認なしで実行します
（`workspace-write` サンドボックスの仕様）。Antigravity CLI の権限要求の形式は、まだ確認していません。

- auris-studio のバックエンドを移植し、4つの CLI を共通トレイトで扱います。
- 実行先（ローカル / SSH 先）とワークスペースを抽象化し、ワーカーごとに git worktree を作ります。
- git と GitHub の操作（ブランチ、コミット、PR の作成とマージ）を自動化します。
- デーモンを常駐させます。ソケットで待ち受け、`--stdio` はそこへの中継にします。こうすると、接続が切れても
  作業は続き、GUI と TUI が同時に同じデーモンを見られます。
- ワークフローとトランスクリプトは `state.json` に保存します。フロントエンドの接続がなく、ターン中の
  エージェントもない状態が10分続くと、デーモンは保存してから終了します。次のフロントエンドが起動し直すと
  状態は戻り、完了済みのステップへのメッセージは、同じ worktree で新しいワーカーを起動します。
  ローカルでは GUI の実行ファイルがデーモンを兼ねるので、起動も終了も意識する必要はありません。

### 3. 指揮官、ワーカー、ワークフローエンジン

状況: 実装済み。偽の CLI を使った e2e テストで、指揮官の計画からワークフローを作り、依存順にワーカーを
走らせ、コミット、修正依頼、評価までを確認しています。実機の CLI を指揮官にした会話と、`gh` による PR の
作成はまだ試していません。

- 指揮官は読み取り専用で起動し、権限要求はデーモンが自動で拒否します。計画は返答の中の ```` ```maestro-plan ````
  ブロック（JSON）で受け取ります。4つの CLI すべてがテキストを出せるので、これを共通の窓口にしました。
- ノードごとにブランチ `maestro/wf{id}-n{id}` とワークツリーを作り、依存ノードのブランチをマージしてから
  ワーカーを起動します。ターンが終わると Maestro がコミットします。
- 公開ベンチマークの数値は同梱していません。`~/.maestro/router.json`（初回に雛形を書き出します）に
  ユーザーが入力します。実績は `~/.maestro/outcomes.json` に記録します。

- 指揮官がユーザーとの会話から DAG を生成し、依存関係の順にワーカーを起動します。
- **会話と作業の非同期化**: 指揮官の計画は、書かれた時点で自動的に走り始めます（`Workflow::started`）。
  指揮官へのメッセージの前には、デーモンが作業の状況（`<maestro-status>`、各ノードの `wf1/n2` 形式の id と
  状態）を差し込みます。指揮官は、新しいタスクが既存の作業の結果を必要とするかを自分で判断し、計画の
  ノードに `"after": ["wf1/n2"]` と書きます。そのノードは、待つノードがすべて成功した時点で、そのブランチを
  マージしたワークツリーで自動的に始まります（`Node::after`、`Command::WaitFor` / `StopWaiting`）。
  他のワークフローを待てるのは、それより前のワークフローだけなので、全体としても DAG のままです。
  ターンの途中に送ったメッセージは、デーモンがターンの終わりまで預かってから渡します（`AgentEvent::Queued`）。
- ノードへの直接メッセージやワークフローの編集は、すべてコアのコマンドとして実装します。
- **ワーカーの自動選択**: 次の情報をもとに、指揮官がプロバイダとモデルを選びます。
  - 公開されているベンチマークスコア
  - 実際の作業での成功と失敗
  - 作業にかかった時間
  - ユーザーからの修正依頼の回数
  - ユーザーの評価
- **難易度に応じた調整**: タスクの難易度から、モデルのグレード（Light / Standard / Frontier）と
  エフォートを自動で決めます。
- **複数モデルでの並列比較**: 余裕があるときは、同じノードを複数のプロバイダ・モデルで同時に走らせ、
  ユーザーが良い方を選びます。各モデルは別々の worktree とブランチ（`maestro/wf1-n2-c1`, `-c2`）で
  作業し、全員が終わるとノードは「Pick one」（`NodeStatus::AwaitingChoice`）で待ちます。選ばれた
  ブランチがノードのブランチになり、依存ノードはそれをマージします。選択は `Outcome::chosen` として
  実績に残り、選ばれたモデルは勝ち、選ばれなかったモデルは負けとして次の選択に効きます。
  - 余裕の判定は `router.json` の `comparison` で決めます。比較するモデル数（`contenders`、1 で無効）、
    比較する最低の難易度（`min_difficulty`、既定は Moderate）、ホストで同時に動くワーカーの上限
    （`max_workers`、計算資源）、プロバイダごとの同時実行の上限（`per_provider`、利用枠）です。
    上限に達していても、比較しない通常の作業は始まります。
  - 比較相手は、別のプロバイダのモデルを優先します。どのモデルが何を得意とするかを学ぶためです。
  - **得意分野の学習**: 指揮官はノードに作業の種類のタグ（`"ui"`, `"tests"` など）を付けます。
    ルーターは同じタグの実績を重く数えるので、UI の比較で勝ち続けたモデルは UI のノードで選ばれやすく
    なります。
  - CLI の残り利用枠を直接読む方法はまだないので、利用枠は `per_provider` の上限で表します。

### プロジェクト

ChatGPT のデスクトップアプリのように、作業環境を「プロジェクト」単位で管理します（`maestro_core::Project`）。

- プロジェクトはリソースを持ちます（`Resource`）: GitHub リポジトリ（`owner/name`）、マシン上のフォルダ
  （git チェックアウト）、SSH 接続先、利用を許可する AI プロバイダ。プロバイダが1つも登録されていない
  プロジェクトはすべてを許可します。各リソースにはプロジェクト内の id（`r1`, `r2`…）が付きます。
- **1 プロジェクトに 1 指揮官**。指揮官はプロジェクトの最初のフォルダ（なければデーモンのホーム下の
  `projects/p1`）を読み取り専用で読みます。動いている指揮官がいる間は新しく起動できず
  （`Command::StartCommander { project, .. }`）、終了した指揮官は次のメッセージで置き換わります。
- 指揮官へのメッセージの前には、リソースの一覧（`<maestro-project>`）と、そのプロジェクトのワークフローだけの
  状況（`<maestro-status>`）が、変わったときだけ差し込まれます。指揮官は計画ごとに `"resource": "r1"`
  と、GitHub リポジトリなら `"machine": "r3"` を選び、迷うときや選択が重要なときはユーザーに相談してから
  計画を書きます（`COMMANDER_INSTRUCTIONS`）。リポジトリが1つだけなら省略できます。
- GitHub リポジトリは、選ばれたマシンの `~/.maestro/checkouts/owner/name` に `gh repo clone` されます
  （2回目以降は `git pull --ff-only`）。ワークツリーはチェックアウトの横の `…-worktrees` に作ります。
- ワーカーのモデル選択は、ホストにインストールされたプロバイダのうちプロジェクトが許可するものに限ります。
  設定画面の「プロバイダの無効化」（`Router::usable`）とは独立で、両方の条件で絞り込みます。
- 指揮官の計画でないワークフローは `Command::PlaceWorkflow` で、プロジェクトのリソースから実行場所を選びます。
- プロジェクトのない古い `state.json` を読むと、既存のワークフローと最後の指揮官を1つのプロジェクトに
  まとめ、それらが動いていたリポジトリをフォルダとして登録します。

### 4. GUI（gpui + Atelier）

- `maestro-gui`（実行ファイル名 `maestro`）。指揮官とのチャットパネル、DAG エディタ、ノードのインスペクタ
  （詳細タブとワーカータブ）からなります。
- DAG エディタは gpui-flow ではなく、Atelier の node_editor の指針に沿って Atelier の部品から組み立てています。
  列はノードの依存の深さ（`Workflow::depths`）から決め、位置はフロントエンド側だけで持ちます。
  ソケットのドラッグで依存を追加し、指揮官が書いた下書きノードはエージェント色の破線と Keep / Remove で示します。
- フロントエンドの写し（`maestro_client::Mirror`）は GUI と TUI で共有します。後から接続したフロントエンドも
  会話を再現できるように、デーモンはエージェントごとのトランスクリプトを持ち（`Command::GetTranscript`）、
  ユーザーが送った文も `AgentEvent::Prompted` として流します。
- テキスト入力は gpui-component の Input を Atelier の色に合わせて使います（Atelier に入力部品がないため）。
- サイドバーはプロジェクトの一覧で、開いているプロジェクトの下にそのワークフローを並べます。タイトルバーの
  フォルダボタンで、会話の横にプロジェクトのリソース（名前、リポジトリ・フォルダ・SSH 接続先、AI
  プロバイダのオン・オフ、削除）を開きます。`--repo` を指定すると、そのフォルダを持つプロジェクトを開き、
  なければ作ります。
- **設定ウィンドウ**: タイトルバーの歯車から開く別ウィンドウで、Atelier の preferences の形（サイドバーの
  ページ、`density.form_width` の列、ステータスバー）に従います。
  - 一般: 表示言語と外観。GUI を動かしている PC の `~/.maestro/preferences.json` に保存し、すぐ反映します。
  - AI エージェント: デーモンのマシンにある CLI とそのバージョン（`Command::ListProviders`）。インストールと
    更新は各プロジェクトが公開しているスクリプトをデーモンが `sh -c` で実行し、出力を
    `Event::ProviderSetup` で全フロントエンドに流します（`Command::SetupProvider`）。プロバイダの利用停止は
    `router.json` の `disabled` に入り、ルーターの候補から外れます。サインインは各 CLI が対話的に行うので、
    実行するコマンドを表示するだけにしています。
  - 作業の割り当て: `router.json` の `comparison` を `Command::SetRouter` で書き換えます。
- TUI（ratatui）は、この後に同じ `maestro-client` の上に作ります。
